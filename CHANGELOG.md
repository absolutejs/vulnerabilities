# Changelog

All notable changes to `@absolutejs/vulnerabilities`.

This file is generated by `absolute-changelog` from the entries in
`changelog/`. Edit an entry, not this file — and add new ones under
`changelog/unreleased/`.

## 0.17.4 — 2026-11-24

### Fixed

- **Text files of several MB are scanned instead of making the scan incomplete**
  The source scan reads text files up to 32 MiB instead of 2 MiB. Real projects commit text files of several MB: a generated search index (4.8 MB), generated data (3.5 MB), an SVG with an embedded image (10.9 MB). Each one over the old limit was left unread, which made the scan incomplete, and production refuses an incomplete scan. Reading them is cheap (an 11 MB file scans in well under a second), and the 64 MiB total and the time budget still bound a scan.

## 0.17.3 — 2026-11-24

### Fixed

- **A due database update no longer times out every dependency scan** (`ScanOptions`)
  Grype's vulnerability database is now updated as its own step before a scan, with up to 15 minutes (`databaseUpdateTimeoutMs`), and the scan then runs with auto-update off under its usual 3 minutes. A new database is about 200 MB to download and several GB to unpack; inside the scan it shared those 3 minutes, so on a busy host every scan was stopped partway through the download and the database never updated. Scans that overlap share one update. If the update fails but the installed database is still fresh enough, the scan goes ahead; if the scan then fails too, the update's error is what it reports.

## 0.17.2 — 2026-11-24

### Fixed

- **Grype's database download no longer fills a small /tmp, and its failures say what Grype said**
  Grype stages its whole database archive (about 200 MB) in the temporary directory before unpacking it into its cache. Hosts that keep /tmp small and in memory (the AbsoluteJS control plane gives it 256 MB, shared with the project's source during a scan) ran out of space whenever a new database was due, and every dependency check came back incomplete, refusing production releases. The download now goes in `download/` beside the database cache (`GRYPE_DB_CACHE_DIR`, or `$XDG_CACHE_HOME/grype`). A failed Grype run now reports the last lines of what Grype wrote to stderr, or that it ran out of time, instead of only the command line.

## 0.17.1 — 2026-11-23

### Fixed

- **A scan result from before 0.17 still fits PublishSecurityScanResult** (`PublishSecurityScanResult`)
  `coverage` and `stop` on `PublishSecurityScanResult` are optional, so a result built before 0.17 (a test double, or a scan relayed from a host on an older version) still type-checks. Scans made by 0.17 always set both.

## 0.17.0 — 2026-11-23

### Added

- **Incomplete scans report the limit or error that stopped them and how much they covered** (`ScanCheck`, `PublishSecurityScanResult`, `SourceScanStop`, `SourceScanCoverage`, `describeSourceStop`)
  An incomplete scan now says why and how far it got. The source check reports the first limit it reached (`time-budget` with the budget, `file-limit`, `byte-limit`, or the files it could not read with each error) and its coverage (files listed, readable, checked, and bytes checked), as `stop` and `coverage` on the check and in a sentence in its `detail` and in the `scan-incomplete` finding. A dependency or image check that cannot finish keeps its advice and adds the actual error.

### Fixed

- **Bun 1.3's version 2 bun.lock is scanned, instead of leaving every scan incomplete**
  Bun 1.3 writes `bun.lock` as `lockfileVersion: 2` (it adds `configVersion` and keeps every package as `["name@version", …]`). The dependency check only accepted versions 0 and 1, so every project with a current Bun lockfile scanned incomplete, which refuses a production release. Version 2 is read like version 1, and an unknown version is named in the check's detail.
